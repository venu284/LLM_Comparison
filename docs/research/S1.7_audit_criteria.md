# S1.7 audit criteria (pre-registration)

_Written 2026-11-20, checkpoint 1 of the S1.7 brief. This file fixes the rules **before** any
response length is computed, any family × model table is built, or any response is read. Later
checkpoints may add results elsewhere (`docs/research/S1.7_audit.md`), but they do not change a
rule here. Any change after this commit is recorded as a dated amendment at the end, with the
reason, and is reviewed by the user before it is used._

Scope: CLAIMS S0.10 (per-family labels), S0.11 (unavailable cells), S0.1 (success = released score
1.0), C4 (no confirmed defect without execution evidence). Nothing here refers to P0.4, P0.5, P0.6
or E0 outcomes, or to any oracle or DimensionBest gain.

## 1. Labels

Each suspected family gets exactly one label.

| Label | Needs |
|---|---|
| **confirmed defect** | Execution evidence **and** a named release-side mechanism (§1.1) on enough sampled cells (§3) |
| **cleared** | Re-execution with tests that match the release's grader (§2) reproduces the released S0.1 outcome on the family's sample at or above the agreement threshold (§3), and every disagreeing cell has a named mechanism |
| **undecided** | Anything else: tests not pinnable (§6), harness inadequate (§3.4), unexplained disagreements, or evidence between the two thresholds |

Undecided is a legitimate result: the family leaves the headline and stays in the sensitivity view
(S0.10). A disagreement between our re-run and the released score is never enough on its own for
a defect (C4).

### 1.1 Mechanisms

A disagreeing cell is one where the released S0.1 outcome (pass: score = 1.0; fail: score < 1.0)
differs from our re-run's outcome. Each is assigned one mechanism, with the log line or response
excerpt that supports it.

Release-side mechanisms (evidence of a grading artefact):
- `extraction`: code extraction or format failure (for example code outside the expected fence,
  several blocks, a different entry-point name than the harness calls);
- `toolchain`: missing toolchain or library in the release's environment;
- `harness_timeout`: harness or timeout error;
- `truncation`: the response is cut off (shown by reading, §4; the length screen in §5.3 only
  flags candidates);
- `test_version`: the wrong test file or version;
- `wrong_field`: the scorer read the wrong field, or the released value is not an execution
  result.

Our-side and neutral mechanisms (explain a disagreement, but are not a release defect):
- `flaky`: re-running the same cell three times gives different outcomes;
- `our_harness`: our sandbox fails to execute the cell (import error from our image, our timeout,
  our runner bug);
- `release_correct`: on inspection the released outcome is right and our run is wrong for a
  stated reason.

A mechanism is named only when the evidence for it is recorded. A plausible guess with no supporting
log or excerpt is recorded as `unexplained`.

## 2. When re-execution counts as matching the release's grader

The release's grader was not found (§9). Therefore (user, 2026-11-20):

- Our re-run counts as matching when it reproduces the released **S0.1 outcome** on the family's
  sample (pass means score = 1.0, fail means score < 1.0). The exact partial-credit value is not
  compared.
- The tests used are those pinned for the family in the evidence plan (§11). The **documented**
  test version is the one the paper names for the family (arXiv 2606.22902v3, Table 5, as quoted in
  `router/data/scoring.py`); where the paper names none, the source benchmark's own release that
  Route Anything's `tasks.jsonl` notes name.
- **Documentary conflicts**, fixed now: only **`humaneval`**. The paper lists HumanEval+ for Code
  Generation; Route Anything's `tasks.jsonl` notes say it verified with "HumanEval base tests
  (humaneval-x Python)". For `mbpp` both sources name MBPP+, so it has one version. No other suspect
  has two documented versions.
- For a conflicted family, the version is identified on a **separate** sample (stream 117 for
  `humaneval`, drawn from the family's frame minus the cells of its main sample). Both versions are
  run there. The release's version is **identified** if one version's agreement exceeds the
  other's by at least 10 percentage points. The label is then computed on the **main** sample
  (stream 116), never on the identification sample:
  - identified version = the documented version: the family is judged on it, by §3;
  - identified version ≠ the documented version: mechanism `test_version` is recorded (the
    release's tests differ from its documentation) and the family is **undecided**, pending a user
    decision on whether grading against that version is acceptable under S0.1. Its main-sample
    agreement under each version is reported;
  - not identified: the family is judged on the documented version, and both agreements are
    reported.
- "Grader unknown" alone does not make a family undecided.

## 3. From sample results to a family label

### 3.1 Quantities (per family, on its uniform sample, §8)

- `n_exec`: sampled cells our sandbox executed to pass or fail (excludes `our_harness` errors).
- `agree`: cells in `n_exec` whose re-run outcome equals the released S0.1 outcome.
- `a = agree / n_exec`, the agreement rate.
- `d`: cells with a release-side mechanism (§1.1), each with its evidence. `r = d / n_exec`.
- `u`: disagreeing cells marked `unexplained`.

Intervals are 95% Wilson score intervals.

### 3.2 Thresholds

- **cleared** if `a ≥ 0.95` and `u = 0`.
- **confirmed defect** if the Wilson lower bound of `r` is **≥ 0.05**.
- **undecided** otherwise.

The two conditions cannot both hold: `a ≥ 0.95` bounds the point estimate of `r` at 0.05, and the
Wilson lower bound lies below the point estimate.

### 3.3 Families without execution

A family that cannot be re-executed (tests not pinnable, harness too costly, or ineligible and not
re-run by decision) cannot be cleared or confirmed (C4). It is **undecided**. Reading results (§4)
are still reported.

### 3.4 Harness adequacy

If `our_harness` errors exceed 10% of the drawn cells, the harness is inadequate for that family
and it is **undecided**, whatever `a` or `r` are.

### 3.5 Stratum samples

Some evidence comes from strata selected by score (the X12b all-zero tasks, CRUXEval's 0.8 cells).
These strata are evidence about mechanisms only. They never set a family's label directly, and a
score-defined stratum is never proposed as a rule (§7).

## 4. Reading protocol

Each sampled cell is read once and recorded in fixed categories **before** any summary is
computed. Categories are filled by a deterministic script written and committed before it is run
on any response; an inspector may add a manual override in a separate column, with a note. The
released score is **not** joined to the reading table until every cell in the sample is
categorised.

| Field | Values |
|---|---|
| `empty` | `yes` (no non-whitespace text) / `no` |
| `code_format` | `fenced_one` / `fenced_many` / `unfenced_code` / `no_code` |
| `truncated` | `yes` (unclosed fence, or text ends inside a code block or mid-statement) / `no` / `unclear` |
| `refusal` | `yes` (declines or asks a question instead of answering) / `no` |
| `language` | `expected` / `other` (code language differs from the task's) / `n_a` |
| `entry_point` | `matches` / `differs` / `absent` / `n_a` (for tasks with a named entry point) |
| `reasoning_only` | `yes` (reasoning text present, no final answer) / `no` |
| `note` | free text, optional |

## 5. Tables, flags and screens (checkpoint 1, released scores and lengths only)

### 5.1 Flagship

The **flagship** models are the three released models with the highest **output price** in
`router/data/prices.py` (`CRB_PRICES[*].output_per_m`; user, 2026-11-20). A tie at the third place
includes every tied model. This definition is fixed before the table is computed.

### 5.2 Family × model table and flags

For every ID family and each of the 8 released models, over **available** cells (the 148
`missing_token_record` cells are excluded and counted): mean released score, share at 1.0 (the
S0.1 success rate), share at 0, and the number of distinct released values. Flags:

- **all-zero family**: every available cell scores 0.
- **flagship below median**: a flagship model's success rate in the family is strictly below the
  median of the 8 models' success rates in that family.
- **values off-rule**: an `exec` family whose S1.4 rule does not state partial credit
  (`partial_credit` is `unstated` or `no`) has any released value outside {0, 1}. (Single-sample
  pass@1 is binary.) The table also reports, per family, the number of off-rule cells, so a flag
  resting on one cell can be told from one resting on many. The flag itself is not thresholded.

Flags on ineligible families are reported but add no suspect, since their labels change no view.
An eligible family newly flagged is added to the suspect list (§11) with the next stream id
(§8.2) and is audited under these same criteria.

### 5.3 Truncation screen

No `max_tokens` setting is known. For each released model, let `M` be its largest released
`output_tokens` over available ID cells. The screen flags cells with `output_tokens ≥ 0.99 · M`,
and reports, per model, how many cells sit **exactly** at `M`. A model has a **pile-up** when at
least 10 cells sit exactly at `M`. The screen only flags cells. Truncation counts as a mechanism
only when reading (§4) shows the response cut off.

### 5.4 Response coverage

For each family and response-matrix key: non-empty responses; empty responses with released
`output_tokens > 0`; empty responses with `output_tokens == 0`; and empty cells with a released
score of 1.0. "Empty" means no non-whitespace text. Presence and length only. These counts feed a
user decision (empty responses: unavailable or failure); no rule is applied to them here.

### 5.5 Model mapping (step 1)

Score-free rules only:

- **Byte identity:** for each pair of keys, the share of tasks where both responses are non-empty
  and byte-identical (compared by SHA-256). Two keys are **aliases** if that share is ≥ 0.99.
- **Length correlation:** for each key and released model, the Spearman rank correlation between
  the response's character length and the released `output_tokens`, over tasks where the response
  is non-empty and the cell is available.
- A key **maps** to a released model when its name equals the model's name and that model has the
  highest correlation in the key's row, or when it is an alias of a key that maps.
- A key with no released counterpart under these rules is reported and carried forward, not used
  for any released model's cells.
- If a released model has two candidate keys that are not aliases, the one with the higher
  correlation is the graded key; if the two correlations differ by less than 0.02, the mapping is
  unsettled and both keys are carried forward to reading and re-execution.

## 6. Tests that cannot be pinned

A family whose release test version cannot be identified and pinned (by commit and checksum) is
**undecided**. The reason is recorded.

## 7. Subset rules

Labels are per family (S0.10). A defect confined to part of a family may be **proposed** as a
subset rule, only on a **non-score property**: a library, a toolchain, Route Anything's `runnable`
flag, an id range. "Every model scored 0" and any other score-defined set are never a rule. The user
decides every subset rule.

A proposal is written as:
- family; the property and its source file; the task count it selects;
- the sampled cells and mechanism evidence that motivate it, and the evidence from outside the
  subset;
- a separate sample drawn from the subset frame with the next free stream id from 140 up, recorded
  before the draw;
- status: proposed, pending the user.

## 8. Samples

### 8.1 Size rule

- Target: a 95% confidence interval on the agreement rate with half-width at most 0.10 at p = 0.5.
  The normal approximation gives `n = ⌈1.96² · 0.25 / 0.10²⌉ = 97` cells.
- **N = 12 tasks** (12 × 8 models = 96 ≤ 97). A family or stratum with N or fewer tasks has every
  available cell with a non-empty mapped response re-run; otherwise `n = 97` cells are drawn.
- Frame: the family's available cells (8 released models × tasks, minus `missing_token_record`)
  whose mapped response is non-empty. Empty responses are covered by §5.4.
- No stratification by model.
- Draw: `numpy.random.default_rng(numpy.random.SeedSequence([0, stream]))`, `choice(frame, n,
  replace=False)` over the frame sorted by (`task_id`, `model`).
- Each disagreeing cell is re-run three times to test for `flaky`.

### Amendment 8 (2026-11-21): CRUXEval value extraction (CLAIMS A2)

Reason: CLAIMS amendment A2 (`main` at `104aa70`) makes CRUXEval success a released score
≥ 0.8. The re-check needs a rule that finds the predicted value in a response that has extra
text. The 2a literal rule (the last `assert f(...) == <literal>`, else the last fenced block,
else the whole text) fails on most reasoning-then-answer responses.

**Not blind.** This rule is written after the 2a reading: CRUXEval responses in streams 109 and
125 were read, and it is known that every 0.8 cell in them (128 of 128) contains the correct
output in its last 300 characters (`S1.7_audit.md`, checkpoint 2a §5). The rule is fixed here,
before the re-check runs, and is not adjusted after it.

The CRUXEval prompt ends: "Give the output as a Python literal inside a code block." The
**candidate** is the first of these that exists:

1. the expression after `==` on the **last** line in the text matching
   `assert\s+f\(.*\)\s*==\s*(.+)` (inside or outside a fence);
2. the **last fenced block** (any language tag or none) whose body does not contain `def f(`:
   its stripped body if that parses as one Python expression (`ast.parse(..., mode="eval")`),
   else its last non-empty line;
3. the text after the **last** `Output:` or `Answer:` label (case-insensitive, `*` and `#`
   around the label ignored) on the same line, or, if that is empty, the next non-empty line;
4. the **last inline code span** (`` `...` ``) that does not contain `f(`.

No candidate: the cell **fails**. Clean-up before comparison: surrounding whitespace, backticks
and `*` are removed, and one trailing `.` is removed when the candidate does not then end in a
digit.

**Comparison**, inside the sandbox: the task's `code` is executed and `result = f(<input>)` is
computed. Then:

- **pass** if `eval(candidate) == result`;
- if `eval` raises, **pass** if `result` is a `str` and `candidate == str(result)` (an unquoted
  string answer, the 2a `our_harness` case);
- otherwise **fail**.

**Judging:**
- **Under A2:** the main sample (stream 109) is judged by §3.2, comparing this rule's outcome
  with released ≥ 0.8. The 0.8 sample (stream 125) is evidence only (§3.5).
- **Strict rule:** 2a's result, the literal rule against released = 1.0, is reported next to it
  as the sensitivity.

Every headline count is given under both rules.
