## 1. Setup and regeneration

```
pipeline/venv/bin/python scripts/fetch_data.py --verify-only      # fetched: 0, verified: 187
pipeline/venv/bin/python router/experiments/e0_power.py           # about 7 minutes
```

The port reuses the P0.5 and P0.6 functions (`load`, `Pop`, `folds`, `crossfit_baseline`,
`cluster_boot`, `ra_routes_fold`, P0.6's `complete_case`, `policy_matrices` and `run_seed`), so the
definitions are the current ones:
- success = score 1.0 (S0.1);
- unavailable cells treated as missing by taking the complete case (S0.11);
- real X13 visible-test verdicts, verifier cost $10⁻⁶ per run (R1, S0.2);
- best single model chosen inside the training folds (S0.3);
- 5-fold cross-fitting by problem (S0.6);
- paired cluster bootstrap over problems, 1,000 resamples (S0.8).

It uses P0.6's seed scheme: fold seed s, bootstrap seed 1000 + s. On seed 0, the CIs of all seven
shared policies equal P0.6's committed output exactly. The script stops if they do not, and a test
checks the committed JSON. Two full runs gave identical output, apart from the runtime field and
the power-at-margin field, which was added between them.

**Draws.** Each policy is scored on 20 fold draws (seeds 0–19), as `power4.py` used 20
repetitions. The pass rates over seeds 0–4 (the S0.8 seeds) move in steps of 20%, so they are
reported separately and the 20-draw figures are used for power.

**What the pass rates mean.** Every draw uses the same data and re-randomises only the folds and the
bootstrap. A pass rate therefore measures how stable a gate verdict is to the draw; it is not
sampling power. The original scripts have the same limitation.

**Power for a router whose true gap is 0.** A router with true gap 0 has its CI lower bound at
or above −m with probability Φ(z·m/h − z), where h is the CI half-width and z = z₀.₉₇₅. The original
scripts' "margin for 80% power" is m₈₀ = (z₀.₉₇₅ + z₀.₈₀)/z₀.₉₇₅ × h = 1.43 h. Both are reported,
the first at m = 2 (the S0.3 margin).

**Populations.**

| Arm | Tasks | Problems | Used for |
|---|---|---|---|
| Headline, complete case | 1,907 | 1,701 | Comparison with P0.5 and P0.6 |
| Headline, evaluation population | 1,514 | 1,347 | What S0.3 is scored on: the complete case minus a 20% development split of the pool's problems (588 of 2,938 problems; 393 headline tasks). The development-split seed (0) is provisional (CLAIMS O6) |
| Pool, complete case | 3,380 (of 3,444) | 2,891 | DP1a. 64 tasks with an empty X13 response dropped; none of the 148 missing Qwen3-Max runs is in this pool |

**Stand-in policies** (headline arms). These are not routers. The rules route by predicted cells,
since the router cannot see the source.
- CellBest with predicted cells (the S0.3(c) comparator, tested here against (a) and (b) only);
- per-cell Rules A and B with no-signal cells accepted or escalated (no oracle; R2 baselines);
- Rules A and B with an oracle decision on no-signal cells (the DP1b bound, not buildable);
- the best fixed ladder in escalate mode. It is picked on the whole set, so it is an in-sample
  pick and its figures are optimistic.

## 4. What this means for the −2 margin

The user chose on 2026-11-19 to keep −2 and report the power with the result. These are the
numbers to report. Nothing here proposes a different margin.

- **(b) against the best single model.**
  - Complete case: a router routing like the no-oracle per-cell policies is measured to ±1.4–1.5
    points, which gives 72–77% power at −2 for a true gap of 0.
  - Evaluation population (the population S0.3 is actually scored on): ±1.8–1.9, power 55–60%.
  - A router that departs from the best single model as much as the oracle-bound policies:
    ±1.9–2.6, power 32–56%.
  - The plan's "about 60–70%" matches the no-oracle case on the evaluation population; routers that
    change more cells have less power.
- **(c) against CellBest.**
  - A router close to CellBest is measured to ±0.3–0.6 points, with power about 1.00 at −2.
  - One that departs as much as the bound policies is measured to ±1.3–2.0, with power 0.51–0.88.
- **(a) and (c) savings.** The saving half-width is 2.0–2.4 points against the best single model
  on the complete case and 3.1–3.2 on the evaluation population for the no-oracle policies.
  Against CellBest it is 0.3–1.6. To pass (a), a router needs a point saving of about 22–23% or
  more; to pass (c), a point saving against CellBest above its half-width.
- **Comparator stability.** The comparator's own saving against the best single model varies by
  17.5 points across development-split seeds (§3.3). The power of (c) is high; how hard (c) is to
  pass depends on the draw.

## 6. Open questions

1. **Development-split seed and S0.3 verdicts.** Because CellBest's strength moves with the
   development split (§3.3), the split seed affects how hard (a) and (c) are to pass. It is
   recorded once (S0.6), so this is not a choice made after results. It should be fixed before any
   router result exists (CLAIMS O6).
2. **Near-ties in CellBest.** Whether the comparator should keep its pure argmax rule or, for
   example, prefer the cheaper model when two are within a CI. This would change the comparator,
   which S0.3 fixes, so it is for the user only (CLAIMS O3).
3. **Pass rates as power.** The draws re-randomise folds on fixed data. A sampling-based power
   estimate (for example, resampling problems before cross-fitting) would measure power directly.
   The original scripts did not do this either.
4. **Population for S3.7.** The script takes the population from P0.5/P0.6's definitions. S3.7 needs
   it to read the S1.4 eligibility and the S1.7 `artefacts.yaml` instead. `--no-p0-6-check`
   exists for that rerun.
