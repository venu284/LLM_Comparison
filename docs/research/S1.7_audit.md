### 7. Decisions for the checkpoint 1 review

- **A. Mapping for glm-5, MiniMax-M2.7, qwen3.5-plus.** §5.5 gives them no graded key, so 3 of the
  8 models (about 30,000 cells) could not be audited at all.
  - Proposed amendment: map a name-equal key that has no alias conflict to its model **by name
    alone**. No score-free check can confirm the mapping for these reasoning models: the length
    correlation fails (§1), and the control shows the characters-per-token check also passes most
    wrong keys. The amendment rests on the key names in the release's own response matrix and on
    the absence of any alias.
  - The alternative is to leave them unmapped. The labels would then rest on five models, and the
    report would say so.
- **B. Qwen3-Max on code_generation.** Both `Qwen3-Max` and `qwen3.6-plus` are carried forward
  for `bcb`, `bcb_v014`, `humaneval` and `mbpp` (brief rule), and both are read and re-run on the
  sampled Qwen3-Max cells there.
  - Outside S1.7, for the reviewer: Qwen3-Max's released `output_tokens`, and so its released cost
    (S0.2), is one constant per family, not a per-response record.
- **C. Empty responses** (brief decision 1): are they unavailable or failures? 895 empty cells
  (name match) carry a released score of 1.0, 850 of them in `lcb`. "Unavailable" would be CLAIMS
  amendment A2 and would change the complete case.
- **D. Suspect scope.** All 20 eligible families except `he_completion` are now suspects:
  - `hex_python` and `mbpp_completion` join on one or two off-rule cells and a flagship below
    the median;
  - the five `bcb*` families, `ds1000` and `humaneval` are in through X12b.

  A family that ends **undecided** leaves the headline, so the headline can shrink a lot. For
  example, if the BigCodeBench sandbox fails §3.4 (more than 10% `our_harness` errors), all 1,097
  BigCodeBench tasks leave it. The flag rules are as pre-registered and have not been changed.
- **E. Stream ids.** S1.7 uses `[0, 100+]`. The plan gives S2.4 `[seed, 2]`, `[seed, 3]`, … with
  no upper bound. Proposed plan text: "S2.4 uses stream ids 2–99; 100 and up belong to S1.7."
- **F. Identical-prompt pairs.** Proposed amendment to §8.2: instead of all 638 differing cells,
  read and re-run a sample of n = 97 of them (stream 129). The 12,080 released comparisons stay

### 3. Mechanisms and their evidence

Assignment rules: `router/experiments/s1_7_mechanisms.py`, applied deterministically to the
recorded cells.

- **BigCodeBench, `toolchain`.**
  - **Pattern:** among sampled cells our harness passes, the release passes none of the tasks
    that import matplotlib (0 of 126), sklearn (0 of 58), seaborn (0 of 39), scipy (0 of 17) or
    wordcloud (0 of 7). Over all 1,097 BigCodeBench tasks, it passes **0.18%** of cells on the 500
    tasks importing those five libraries, against 41.3% on the other 597.
  - **Disclosure:** the five libraries were chosen by looking at the release's pass share per
    library. Other libraries also sit near 0%: `ast` (standard library) 0 of 184 cells, `flask` 0
    of 120, `django` 1.6%, `pytz` 1.7%.
  - **Probe `block_sci`:** the task's own code cannot import the five libraries, installed after
    BigCodeBench's `reliability_guard`. It reproduces the release on all 309 sampled
    five-library cells, including the 161 where our run passes. It leaves the 89 release-pass
    cells on other tasks passing. It also explains 10 of 31 release-fail / our-pass cells on other
    tasks (indirect imports) and 5 of 13 on `ast`/`flask`/`django`/`pytz` tasks.
  - **Rule:** a release-fail / our-pass cell whose probe run reproduces the release is assigned
    `toolchain`. The rest stay `unexplained`: 21 across the five families.
  - **Caveat:** BigCodeBench's own `reliability_guard` imports `matplotlib.pyplot`, so a release
    environment simply lacking matplotlib would have failed every task under the official
    harness. The precise environmental cause is not named; the probe shows only that the release
    behaves as if the task's code could not use these libraries.
- **LiveCodeBench, `harness_timeout` (call convention).**
  - On LeetCode-style (functional) tasks the release passes none of 131 sampled cells, while
    LiveCodeBench's own tests pass 78. AtCoder tasks agree closely.
  - Across the family the release passes 9.2% of LeetCode cells (309 of 3,376), against 50.9% on
    AtCoder.
  - The probe `lcb_stdin` runs every task as a stdin program, never calling `Solution().<fn>`. It
    reproduces the release on 189 of 194 sampled cells, including all 78 release-fail / our-pass
    cells.
- **DS-1000, `extraction`.**
  - Our harness uses DS-1000's own `postprocess`. Responses ending in `</code>` pass it in 11 of
    16 sampled cells, but the release passes 0 of 16.
  - The probe `ds_raw` executes the response with no extraction. It reproduces the release on 177
    of 194 cells, and on 73 of the 87 where our harness passes and the release fails. The rest
    stay `unexplained`.
- **CRUXEval, `our_harness` (8 cells).** Unquoted string answers (`Fred*Smith`) cannot be
  evaluated as a literal; the release evidently compares them as strings. This is our side.
- **HumanEval, `test_version` (1 cell).** The response fails both HumanEval+ and the base tests,
  yet the release passed it.
- **HumanEval, cell by cell:** the 4 `unexplained` HumanEval+ disagreements all pass the base
  tests, which fits the release grading with base tests. The base path disagrees on a different
  task, HumanEval/50, for 4 models that HumanEval+ passes. That points to a quirk in our "base"
  path (HumanEval-X's tests and prompt), a harness note.
- **HumanEval test version (§2).** On the identification sample (stream 117), agreement is 0.927
  with HumanEval+ and 0.907 with the base tests, a gap under 10 points. The version is **not
  identified**, so HumanEval is judged on the documented HumanEval+. Main-sample agreement is
