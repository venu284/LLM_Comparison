Sufficiency Router Charter

Routing stops asking which model is best and starts asking whether the cheap one is good enough — then learns to answer that for models it has never seen.

65-task web-dev benchmark5 models · 325 runsH4 refuted, repurposed as motivation

The goal00

One sentence

Build a constraint-aware LLM router for code generation that predicts whether a cheap model is sufficient, generalises to unseen models via a bounded measurement probe, and accepts the user's own API keys.

The unit of success is cost per accepted task — not cost per token, and not benchmark pass rate.

Why this, why now01

Market

The bill arrived

Enterprise LLM API spend passed $8.4B, projected $15B by end of 2026, driven by agentic workloads. The pattern is: give every engineer a coding agent, discover the bill, restrict access. Gateways report 40–60% cost reductions.

Research

The field moved

2026 shifted routing from one-shot prompts to execution-aware decisions, and the metric from cost-per-token to cost-per-accepted-task. The named open problem: routers are trained per-pool and die when the pool changes.

Our evidence

We measured the premise

Phases 5–6 independently confirmed that prompt-level selection saturates. Oracle selection ceiling is +8.6% over always-best-single; the pre-registered H4 (>15%) is unreachable by construction.

That refutation is now the motivation, not damage. It is a stronger opening than H4 passing would have been.

Decisions — locked02

Re-opening any of these requires a new decision record, not a conversation.

D1

The claim is sufficiency, not selection

Not "which model is best for this task" but "is the cheap model good enough, and if not, what do I spend next?" Selection is refuted on nested pools. Sufficiency is not.

D2

Never learn model identity

The router learns f(task_features, model_descriptor) → outcome, never f(task) → model_id. Identity-based routers cannot accept a model they weren't trained on. This single constraint is what makes BYOK possible at all.

D3

Descriptors are measured, not described

A capability vector comes from executing a bounded probe set against the endpoint and observing outcomes — not from an LLM writing a description of the model. This is the novelty.

D4

Black-box only

Computable from ordinary chat-completion responses. No logprobs, no hidden states, no provider-specific fields — an arbitrary OpenAI-compatible endpoint may expose none of them.

D5

Every learning signal is automated

Test outcomes, compile/typecheck/lint. No hypothesis depends on recruiting human evaluators. Phase 7 is the standing proof: apparatus fully built, zero votes collected across multiple sessions.

D6

Constraints are set by the user, not learned

w_cost, w_latency, w_quality are a weight vector the user supplies. Personalisation is out of scope — a cold-start problem with no data. "Self-correcting" means the route policy improves from pooled execution outcomes, never that the system learns individual taste.

D7

Cost is modelled, with a mandatory sensitivity sweep

All five models are free-tier; estimated_cost_usd is 0.000000 in all 325 rows. Published $/M rates are defensible only if every headline number carries a price-sensitivity analysis.

D8

Nesting is a feature now

"Do not swap in stronger models to rescue H4" stands. Selection needs complementarity; cascade and sufficiency-thresholding want nesting. Changing the pool would weaken the new design.

D9

Two research components, everything else thin

C2 (probe profiling) and C4 (sufficiency predictor) carry the contribution. Ingress, policy engine, and feedback plumbing are features LiteLLM, Bifrost and Portkey already ship. Demo-grade. No chapters.

D10

Disclose, never repair

Nothing is written back to the runs table. Phase 5 rows stay as published. Corrections are disclosed and re-run, never silently amended.

Hypotheses04

Replaces H1–H4 as the active set. H1/RQ1 (specialization exists) and H4 (selection refuted) are retained as established background.

H-A · Is cheap-model sufficiency predictable?

Task features plus a measured descriptor predict whether a cheap model produces a passing solution, materially better than chance. Target: held-out AUC ≥ 0.70.

H-B · Does the policy transfer to unseen models?

A router trained on pool A, given only a k-task probe descriptor of an unseen model M, retains most of the CPAT reduction achieved by an otherwise-identical router that had M in-pool. Target: ≥80% retained.

Measured on a public corpus (E2), not on our 65-task matrix — and that distinction matters. Our pool is nested, so there is no in-pool routing gain here to retain 80% of; C2's probe sweep below shows argmax-over-descriptor flat at ~52% for every k. H-B is defined against cost reduction at held pass rate, the quantity D1 actually optimises, and evaluated where a measurable in-pool gain exists.

H-C · Measured descriptors vs. generated ones the novelty

GraphRouter (ICLR 2025) already generalises to new LLMs — by using "a generative LLM such as GPT-4o to generate a descriptive text for each LLM, outlining key details such as its strengths, token pricing, and context length," embedded with BERT.

That is reputation, not measurement. It has four failure modes, and all four are exactly the BYOK case:

Failure 1

A user's private fine-tune — no describer has heard of it.

Failure 2

A model released after the describer's knowledge cutoff.

Failure 3

A self-hosted or quantized endpoint that behaves unlike its model card.

Failure 4

Two models with similar descriptions and different real behaviour.

Design: same router, two descriptor sources, head-to-head — stratified by whether the model sits inside or outside the describer's knowledge. This is the contribution nobody owns.

Price provenance

Groq list rates are confirmed for Llama-3.1-8B ($0.05/$0.08), Llama-3.3-70B ($0.59/$0.79) and GPT-OSS-120B ($0.15/$0.60). Rates for Llama-4-Scout (~$0.11/$0.34) and Qwen3-32B (~$0.29/$0.59) are unconfirmed — †-marked rows rest on them and must be re-checked before publication. The headline result — Llama-3.1-8B → GPT-OSS-120B at 56.9% / −10.8% — uses only confirmed prices and stands regardless. Six decimals reflect arithmetic precision, not measurement precision; the prices themselves are modelled (D7).

The oracle figure is inflated — decompose it

68.4% of that −78.8% comes from the oracle clairvoyantly declining to attempt the 27 tasks (42%) no model solves. A real router does not get that free.

Realistic target: ≈ −25% cost, against fixed cascade's already-banked −10.8%. Claim −25%, not −79%.

H-E · Is "don't spend at all" a useful action?

Unsolvable rate is 5% on easy, 60% on medium, 56% on hard — difficulty separates it strongly. Claim discipline: abstention reduces spend, it does not raise pass rate. Report as "N tasks flagged out-of-pool," never folded into a pass-rate number.

Architecture05

C2 · Probe profiling research core

User supplies endpoint and key. System runs the probe set — k tasks, executed and verified — and emits a measured descriptor: pass rate per category × difficulty cell with marginal backoff, verbosity, latency, truncation rate, format compliance, price. Bounded, disclosed upfront, charged to the user's own account.

The descriptor wants 5 categories × 3 difficulties = 15 cells, so k in the 12–15 range gives roughly one sample per cell — almost certainly too noisy. Let experiment E4 set k; do not assume it.

C6 · Verification ladder

RungSignalQualityAvailability
1User's own test suitebestwhen the repo has tests
2Generated testsnoisyalways
3Compile / typecheck / lintweakalways
4Explicit accept / rejectcleansparse

Every rung is automated (D5). Use the graded signal, not the binary one — on the existing 325 runs, 128 (39%) sit between 1% and 99% of tests passing, and every published number binarises them to "fail." A rich continuous quality signal already paid for and never spent.

The honest hard part

For a general BYOK app on an arbitrary user prompt there is no test suite, so rungs 2–3 are all you get and they are weak. The self-correcting loop is strongest where executable verification exists. State this boundary explicitly and scope the evaluation inside it — a committee will respect a stated boundary and will not respect a claim that it works everywhere.

Metrics08

Secondary: pass rate · p50/p95 latency · escalation rate · abstention precision and recall · descriptor accuracy · regret vs. oracle as feedback accumulates (the learning curve).

Latency is not free: on the existing matrix 8B → GPT-OSS costs +21% latency for its −10.8% cost. That trade gets shown, not hidden.

Reporting discipline — every cost number carries a price-sensitivity sweep (D7); abstained tasks are reported as flagged, never folded into pass rate; the oracle is always decomposed, never quoted as a single headline.
